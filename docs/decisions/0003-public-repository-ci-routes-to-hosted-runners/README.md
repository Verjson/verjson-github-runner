# 0003 — Route this public repository's CI to GitHub-hosted runners

- **Date:** 2026-08-05
- **Issue:** Verjson/verjson-github-runner#107
- **Category:** CI routing / runner-group admission boundary
- **Status:** Accepted

## Context

This repository's own CI silently stopped running two required checks. Between
2026-08-04T03:21Z (last success) and 2026-08-04T12:25Z, every `changelog /
validate` and `privileged_merge` job entered `queued` with no runner and stayed
there. No check failed, no error was raised, and no run was cancelled — the jobs
simply never received a runner, so pull requests sat `BLOCKED` on checks that
could never resolve.

The cause is an admission boundary, not capacity. On 2026-08-04 the shared
persistent lane moved from the retired `GCP` runner group to group 8
`DigitalOcean`, whose allowlist names 89 **private** repositories and sets
`allows_public_repositories: false`. This repository is **public**. It was
therefore not in the allowlist, and could not have been: the group refuses
public repositories by configuration.

Meanwhile the org routing variables send work here anyway. The canonical
`changelog-validate.yml` resolves its runner as:

```
inputs.runner       — if the caller passed one, else
'ubuntu-24.04'      — if the owner is not Verjson, else
vars.VERJSON_RUNNER_DEFAULT     — if the repository is private, else
vars.VERJSON_RUNNER_UNTRUSTED || vars.VERJSON_RUNNER_DEFAULT
```

For a public Verjson repository the last branch applies, and the org sets
`VERJSON_RUNNER_UNTRUSTED = ["self-hosted","general"]` — the shared persistent
lane. So a public repository is routed to a group that denies public
repositories. The result is a permanent queue: the exact silent-deadlock
signature of Verjson/.github#182, and the failure mode #115 exists to detect.

The terminal `'["self-hosted","general"]'` in that chain is a **hardcoded
literal**, not a variable. This is the detail that makes recurrence silent: an
absent or renamed variable does not fail, it falls back to the dead lane.

`ai-privileged-merge.yml` reaches the same place by a different route. It is a
generated caller that **hardcodes** `runner_labels: '["self-hosted","general"]'`
rather than reading a variable, so no variable change can redirect it.

## Decision

Route this repository's reusable-workflow jobs to GitHub-hosted runners.

1. Set repository-level variables, which override the org values for this
   repository only. These are exactly the four that the org reusable workflows
   actually read:

   ```
   VERJSON_RUNNER_DEFAULT   = ["ubuntu-24.04"]
   VERJSON_RUNNER_UNTRUSTED = ["ubuntu-24.04"]
   VERJSON_RUNNER_ISOLATED  = ["ubuntu-24.04"]
   VERJSON_RUNNER_FASTLANE  = ["ubuntu-24.04"]
   ```

   `VERJSON_LANE_*` variables exist at org level but are referenced by no
   workflow, script, or action in `Verjson/.github@main`. Setting them here
   would imply coverage this repository does not have, so they are deliberately
   **not** set.

2. Regenerate `ai-privileged-merge.yml` with the canonical generator at
   `Verjson/.github` — `gen-privileged-merge-caller.sh '["ubuntu-24.04"]'` —
   rather than hand-editing the label, because the job key, `uses:` target, and
   `with:` values fail silently when wrong.

3. Add a `routing-guard` job to `test.yml` asserting all four variables. The
   callees' terminal fallback is a hardcoded literal rather than an error, so a
   deleted or renamed variable would otherwise reinstate the queue-forever
   deadlock with no signal at all. The guard turns that into a failing check.

   An in-repo pin is not available for the changelog caller: `changelog.yml` is
   generated by `gen-changelog-caller.sh`, which takes **no** runner argument,
   so hand-adding `with: runner:` would drift from canon. The variable plus this
   guard is the correct mechanism there.

The alternative — admitting this repository to group 8 and enabling public
repositories on it — is **rejected**. That group carries persistent, shared,
non-ephemeral runners. Enabling public repositories would expose them to fork
pull requests, which is precisely what the `isolated` lane
(`ephemeral`, `untrusted-pr`, `no-host-docker`) exists to contain. Restoring one
repository's checks is not worth converting a shared persistent lane into a
target reachable by untrusted contributors.

## Consequences

This repository's CI no longer depends on the runner fleet whose image it
builds. That dependency was circular: a defective image published from here
could disable the CI needed to publish the fix. Losing it is a benefit, not a
cost.

The repository's workflows were already partly GitHub-hosted — `test.yml`,
`image-build-check.yml`, and `publish-images.yml` all pin `ubuntu-latest` or
`ubuntu-24.04` directly. This change makes the remaining reusable-workflow jobs
agree with that existing choice instead of inheriting an org default written for
private consumers.

Only `changelog / validate` and `privileged_merge` move. The CI that actually
validates the image — `test.yml` and `image-build-check.yml` — was already
GitHub-hosted and is untouched, as is publication. Image provenance is
unaffected either way, since attestations bind the `publish-images.yml` signer
identity rather than the runner that produced the image.

The privileged merge for this repository now executes on a GitHub-hosted runner.
This is not a weakening. The callee performs no `actions/checkout`, so untrusted
head content never reaches the runner and runner choice is not load-bearing for
code isolation; `ORG_ADMIN_TOKEN` moves from a persistent shared host to an
ephemeral VM, which reduces token residue and co-tenancy exposure. Trust logic
is unchanged — it lives entirely in `Verjson/.github@main`, which the caller
pins as its trust anchor, and the caller still grants exactly one secret rather
than its whole store. The callee also re-validates `runner_labels` against the
same charset restriction the generator applies, so a drifted caller cannot
inject through it.

**This change cannot unblock its own pull request.** On `pull_request_target`,
GitHub resolves the workflow file from the **base** branch, so the first PR
carrying it still runs `main`'s self-hosted copy and its `privileged_merge`
check queues forever. The first merge must therefore be manual
(`gh pr merge --squash --admin`); every subsequent PR resolves normally. Anyone
who meets that wall should read it as the bootstrap, not as the fix having
failed.

Two residual paths still depend on values this repository does not fully
control. `VERJSON_RUNNER_ISOLATED` is the fallback at the callee's `runs-on`
and is reachable if the privileged-merge caller is ever regenerated without
`runner_labels`, or if this repository is made private; it is pinned at
repository level as insurance. `VERJSON_RUNNER_FASTLANE` is org-controlled and
carries the public-repository gate path — it is pinned here too, but an org-side
repoint would still be felt by any repository that has not pinned it.

## Follow-up

The org-level defect is narrower than it first appears, and is not fixed here.
`ai-review-merge.yml:171` already routes public repositories to
`VERJSON_RUNNER_FASTLANE` (`["ubuntu-24.04"]`) before it ever consults
`VERJSON_RUNNER_UNTRUSTED`. The two changelog reusables —
`changelog-validate.yml:26` and `changelog-release.yml:58` — **lack that
`private == false` branch**, and are the only place public work is aimed at the
persistent lane.

So the correct upstream ask is to add the FASTLANE-for-public branch to those
two workflows so they match the gate. Repointing `VERJSON_RUNNER_UNTRUSTED`
itself would be wrong, because it would also change private-repository routing.

The "fails closed by accident" observation still stands and is the reason this
matters: the group denies public repositories, so today the mismatch produces a
dead queue rather than untrusted work on shared persistent hosts. Anyone who
"fixes" the queue by enabling public repositories on that group converts an
accidental fail-closed into a genuine fail-open. Reported as
`Verjson/.github#395`.
